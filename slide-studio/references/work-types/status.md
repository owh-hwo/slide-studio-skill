# Work type: project status / go-live readiness report

The steering group must see in one minute whether the project is on track, what is not, who
is fixing it, and what they must decide. The structure stays identical from one report to the
next so changes stand out.

## Extra interview questions

- Reporting period and data cut-off date.
- Plan baseline: milestones, budget, scope as approved (the comparison point).
- Workstreams to report (3 to 6) and their owners.
- RAG definitions in use (what makes a workstream amber or red). Ask; do not invent.
- Risks and issues log: where it lives; which items go to this audience.
- Decisions needed from this meeting.
- Previous report (reuse its structure and wording where possible).

## Storyline skeleton

| Part | Slides | Pattern |
|---|---|---|
| Cover: overall status in the title ("On track for go-live on 1 March; testing one week late") | 1 | cover |
| Summary: KPIs vs plan | 1 | kpis (one `.focus`) |
| Workstream status | 1 | table.big with `.rag` and band rows |
| Milestones / phase | 1 | phases |
| Top risks and issues with owner and date | 1 | table |
| Decisions needed | 1 | compare or card.brand |
| Next period plan | 1 | steps or table |
| Appendix: detailed plan, defect stats, budget | any | table |

## Go-live readiness variant

Replace workstream status with a readiness checklist (`.ck` or table with RAG): data
migration, testing sign-off, training, cut-over plan, support model, rollback plan; end with
the go / no-go decision slide.

## Pitfalls

- Green everywhere with a late milestone: the title must say what is late.
- Changing RAG definitions between reports.
- Risks without owners or dates.
